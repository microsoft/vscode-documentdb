# Dual-DX Command Design — one tool, two consumers

The founding principle: a modern CLI serves **two consumers with genuinely different needs — humans and AI agents** — and we design for both from day one, in the same binary. They're **orthogonal, not opposites**: keep every human convenience, add agent-grade paths underneath.

Headline: **"Humans typo. Agents hallucinate. The failure modes are completely different."**

## Human DX vs Agent DX

| Dimension | Human DX | Agent DX |
|---|---|---|
| **Input** | Friendly flags (`--db`, `--profile prod`) | Raw JSON payloads (`--json '{...}'`) — zero translation loss, trivially generated by a model |
| **Output** | Tables, prose, color | **Structured JSON / NDJSON always**, plus **structured exit codes** so the agent branches without parsing prose |
| **Discovery** | `--help`, docs, examples | Runtime schema introspection + pre-loaded **Skills** (`SKILL.md`) |
| **Context window** | Irrelevant | Field masks + paging + hard result caps — token budget is a first-class constraint |
| **Trust** | A typo, easily caught | *The agent is not a trusted operator* — hallucinated IDs, prompt injection in returned data; needs `--dry-run`, input hardening, output redaction |

## What this means for the command surface (parameter conventions)

The same command exposes **both** an ergonomic human form and a lossless agent form:

```bash
# Human form — friendly flags, pretty output
documentdb query --profile prod --db orders "SELECT * FROM c WHERE c.status='open'"

# Agent form — same command, structured everything
documentdb query --profile prod --json '{"db":"orders","query":"SELECT * FROM c WHERE c.status=\"open\""}' --format json
```

Conventions we intend to hold:

- **`--json '{...}'` payload input** as the agent-friendly path alongside human flags — one maps losslessly to the underlying API; the other is convenient to type.
- **`--format json|ndjson|table`** with a safe default; agents get structured output every time, humans get tables.
- **Structured exit codes** (distinct codes for auth failure, not-found, connectivity, etc.) so an agent can branch on the code, not the message text.
- **Stable, machine-readable errors** — an agent should never have to parse English to know what went wrong.
- **`--dry-run`** on mutations; **confirmation gates** on destructive operations.
- **Output discipline** — results are structured and PII-aware; secrets/connection details are redacted from all output (an agent reads tool output back into its context).
- **Connections referenced by name, never by connection string** (see [`auth-model.md`](./auth-model.md)).

## Why it's one binary (not two tools)

The human REPL and the agent's repeated calls run the **same execution core** underneath — only the front-end (interactive terminal vs stateless invocation vs daemon client) differs. That's what makes "first-class for both" affordable: the command logic exists once; the audiences get different *skins* over it. See [`execution-modes.md`](./execution-modes.md).

## Skills (how the agent learns the surface)

Agents don't read `--help`. We ship **`SKILL.md`** files that teach an agent the command surface, the JSON payload shapes, the exit-code meanings, and the behavioral rules (e.g. *reference connections by name; never ask the user to paste a connection string into chat*). Skills are the agent's equivalent of docs + muscle memory, loaded into its context on demand.
