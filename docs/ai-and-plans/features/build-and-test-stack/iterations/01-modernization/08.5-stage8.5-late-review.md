## Findings

### S85L-F01: a manual fast run can satisfy the ready-PR merge gate

- **Severity:** medium.
- **Validation:** Traced all workflow events and ran the gate shell against 14 fast, standard, full, failed, cancelled, skipped, and plan-failure combinations. All 14 behaved correctly within one run. GitHub required checks identify a check context by its name and app on the commit, not by the event that created it. A `workflow_dispatch` on a same-repository PR branch uses the selected branch commit, chooses `fast` when `enforce_full_run` is false, and still publishes a successful check named `Merge gate`. The existing truth table cannot detect this cross-run collision.
- **Where:** [main.yml](../../../../../../.github/workflows/main.yml#L29), [main.yml](../../../../../../.github/workflows/main.yml#L94-L100), [main.yml](../../../../../../.github/workflows/main.yml#L554-L581), [build/verification/README.md](../../../../../../build/verification/README.md#L38-L45), [decisions.md](../../decisions.md#L187-L193).
- **What is wrong:** A ready PR is meant to require the standard tier. If its standard run fails, is cancelled, or has not completed, a maintainer can dispatch the same workflow on that PR branch with the default input. Static checks and unit tests can pass, packaging, package checks, L1, and L3 are skipped by design, and the final job still reports `Merge gate: success`. Because the required context does not encode the event or tier, that fast result can satisfy the ruleset even though the ready-PR tier was not successful. This restores the policy bypass that decision 0013 was intended to remove, through a different event.
- **Solutions:** (1) Give manual fast runs a non-required name such as `Merge gate (manual fast, not PR gate)`, while retaining `Merge gate` for manual full runs. **Pros:** preserves the useful fast diagnostic and allows a manual full run to provide equal or stronger evidence. **Cons:** adds another event-sensitive name expression and matrix case. (2) Make every manual run standard or full and keep the current name. **Pros:** simplest required-check semantics. **Cons:** removes the cheap manual fast option and uses more runner time. (3) Split manual diagnostics into a separate workflow whose jobs cannot share the required context. **Pros:** strongest separation. **Cons:** duplicates orchestration and documentation.
- **Recommended:** 1. Add a cross-event matrix case for a failed standard run followed by a passing manual fast run on the same PR commit, in addition to the existing per-run truth table.

### S85L-N01: the installed-VSIX self-test does not prove the new declared-command gate can fail

- **Severity:** low.
- **Validation:** The offline assertion tests reject a fabricated missing command, and the real probe compares `contributes.commands` with `vscode.commands.getCommands(true)` after activation. The product-manifest check passes `declaredCommands(product)` back as the observed command list, so it is tautological. The installed-VSIX negative control registers every late command and then injects a swallowed error; it proves the log gate, not omission of a declared runtime registration.
- **Where:** [checks.cjs](../../../../../../build/verification/activation/checks.cjs#L20-L25), [checks.cjs](../../../../../../build/verification/activation/checks.cjs#L72-L93), [activation.test.cjs](../../../../../../build/verification/activation/activation.test.cjs#L120-L134), [activation.test.cjs](../../../../../../build/verification/activation/activation.test.cjs#L616), [runner.cjs](../../../../../../build/verification/activation/runner.cjs#L210-L219), [probe/tests.cjs](../../../../../../build/verification/activation/probe/tests.cjs#L40-L47).
- **What is wrong:** The checker is small and the positive CI run is useful, but no negative real-host run demonstrates that an installed VSIX with one contributed handler omitted is rejected specifically by `assertDeclaredCommands`. The self-test can remain green if the production integration stops distinguishing manifest contribution from runtime registration.
- **Solutions:** (1) Add a proof mode that suppresses registration of one representative contributed command in the temporary installed entry point, lets activation finish, and requires the probe to fail with `Declared commands not registered after activation`. **Pros:** proves the exact installed-artifact boundary and VS Code API behavior. **Cons:** adds another real-host proof launch or a second mutation mode. (2) Keep only the current offline fixture. **Pros:** no CI cost. **Cons:** continues to prove the helper with a fabricated command list rather than the production integration.
- **Recommended:** 1 when `build/verification/activation/**` changes, consistent with decision 0003.

## Checked and sound

- The aggregate gate includes every job that can be expected by the plan. Its shell rejects failed, cancelled, and unexpectedly skipped static checks, unit tests, package checks, packaging, L1, and L3. A failed plan produces an empty tier and still fails the gate. An unrelated-label event runs the gate under `Merge gate (label event, not run)`, so it does not replace the required context.
- Tier selection and path detection cover draft and ready PRs, full-label requests, pushes, manual runs, renamed files, API limits, initial pushes, and API failure. Fork PR jobs execute with read-only tokens; comment and checkout steps that need same-repository trust are guarded. No event-controlled string is interpolated into a shell program.

Pull-request caches are scoped to the pull request merge ref, so a fork or same-repository PR cache cannot be restored by a later `main` push.
