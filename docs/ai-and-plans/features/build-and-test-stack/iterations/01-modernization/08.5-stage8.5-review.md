## Findings

### S85-F01: the sole required check can pass or be skipped while expected CI fails

- **Severity:** medium.
- **Validation:** Read-only GitHub API queries on 2026-10-14 confirmed that the active `main`, `feature/**`, and `release/**` rulesets require only `license/cla` and `Build & Package`. Source inspection covered draft, manual, standard, full, unrelated-label, upstream-failure, and independent verification-job paths.
- **Where:** [main.yml](../../../../../../.github/workflows/main.yml#L22), [main.yml](../../../../../../.github/workflows/main.yml#L80), [main.yml](../../../../../../.github/workflows/main.yml#L188), [main.yml](../../../../../../.github/workflows/main.yml#L205), [main.yml](../../../../../../.github/workflows/main.yml#L322), [main.yml](../../../../../../.github/workflows/main.yml#L387).
- **What is wrong:** W1 changes the job name only for unrelated-label runs. Draft PRs and ordinary manual dispatches still skip a job named exactly `Build & Package`, and GitHub treats a skipped required job as satisfying the required context. In standard and full runs, that job needs only `plan` and `code-quality-and-tests`; `package-checks`, L1, and L3 are independent or downstream jobs, so any of them can fail while the required job remains successful. If L0 fails, the required job is skipped through its `needs` dependency, the known pre-Stage 8.5 weakness recorded in the plan. The ruleset therefore does not enforce the tier that the report says ran.
- **Solutions:** (1) Rename the artifact-producing worker and add a final `Build & Package` aggregate job with `if: always()` that evaluates the plan and every expected job result, failing on a failed, cancelled, or unexpectedly skipped layer. **Pros:** one stable required context enforces all tier-specific work and handles path-scoped skips deliberately. **Cons:** adds a small result-validation step. (2) Require every verification job in all three rulesets. **Pros:** direct GitHub enforcement. **Cons:** path-scoped names and future E2E lanes make the rulesets brittle, and fast tiers need carefully designed neutral jobs.
- **Recommended:** 1, with event-matrix tests for draft, ready, manual-fast, manual-full, unrelated-label, path-scoped failure, L0 failure, fork PR, and cancelled jobs.

### S85-F02: the merged report loses the requester and link for the last full run

- **Severity:** medium.
- **Validation:** Generated a full report and then a standard report through `ciReport`. The full report identifies the requester through its reason and links its workflow run. The replacement standard report retains only the full run's SHA and result. The seven report tests assert only those two retained fields.
- **Where:** [decisions.md](../../decisions.md#L129), [ci-report.cjs](../../../../../../build/verification/ci-report.cjs#L10), [ci-report.cjs](../../../../../../build/verification/ci-report.cjs#L84), [ci-report.cjs](../../../../../../build/verification/ci-report.cjs#L89), [ci-report.test.cjs](../../../../../../build/verification/ci-report.test.cjs#L92).
- **What is wrong:** Binding decision 0002 requires the report to record who requested a one-shot full run, the commit, and a link to that run. `LAST_FULL` serializes only SHA and result, and `fullRunLine` renders only those fields. The next fast or standard report replaces the full report, so the requester and full-run URL disappear; its workflow link points to the newer non-full run instead. This weakens the audit trail the one-comment design was meant to preserve.
- **Solutions:** (1) Store SHA, result, requester, and run URL in a versioned hidden marker and render all four in the last-full line. **Pros:** satisfies the decision and keeps one comment. **Cons:** needs safe parsing and compatibility with the existing two-field marker. (2) Keep a separate immutable comment for each requested full run. **Pros:** natural history. **Cons:** reverses the operator's merged-comment decision and creates comment noise.
- **Recommended:** 1, with tests for a full run followed by fast and standard runs, and for a stale full run finishing after the PR head changes.

### S85-N01: a stale first full run can create a report for an obsolete head

- **Severity:** low.
- **Validation:** Traced the report job branches with `stale === true`, `plan.tier === 'full'`, and no existing `<!-- ci-report -->` comment. That case bypasses both stale branches and calls `createComment` with the stale run's complete body. The stale-run test starts with an existing newer report and does not cover this case.
- **Where:** [main.yml](../../../../../../.github/workflows/main.yml#L493), [main.yml](../../../../../../.github/workflows/main.yml#L502), [ci-report.test.cjs](../../../../../../build/verification/ci-report.test.cjs#L171).
- **What is wrong:** The source comment says an older run must not replace a newer report, but the first report can still describe an obsolete commit until a newer run successfully posts. If the newer run never reaches the report job, the stale body remains the PR's only CI summary.
- **Recommended:** Handle stale full runs before the create/update split. When no comment exists, create a neutral current-head report or defer comment creation while preserving the full-run provenance for the next current-head report. Add the missing no-existing-comment test.

## Complexity Judgement

Stage 8.5 reduced complexity overall. W2 and W4 remove roughly one thousand lines of migration scripts, timing tests, exact generated-shape matching, and obsolete flags while retaining discriminating controls. W3 makes the ESM-only boundary explicit, and W5 gives current intent a navigable feature home. W1 necessarily adds orchestration and one 152-line report formatter; that is proportionate to tiered CI, not general over-engineering. Its weak point is architectural rather than size: the required check and last-full marker are not yet authoritative enough for the policy they represent. Fixing those two contracts should not require expanding the system beyond one aggregate gate and a richer marker.
